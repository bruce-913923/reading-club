機場安檢大家都排過。安檢的每一道檢查，背後都有它的來歷。

像隨身液體要限量，是 2006 年英國破獲液體炸彈陰謀之後才開始的，等於是出了事才加上去。

有些檢查是分級的。美國有 PreCheck，事先審過背景的人可以走快速線，TSA 自己說這是依風險來做的安檢，不是每個人都要做全套。

誤報也有成本。儀器一響，就可能要搜身，後面整排的人一起等。

有些規則後來也會取消。2001 年有人把炸藥藏在鞋子裡，美國從 2006 年開始規定要脫鞋，到 2025 年 7 月取消了，官方講的理由之一就是要縮短排隊時間。

寫 code 也一樣。現在人看 code 越來越少，我的 PR 最多同時有 5 家 AI 在審，那到底要設幾道安檢？讀書會的題目問的就是這個。

02｜AI 開發流程到底需要多少 Checker？

  • 探討問題：如果人工 Code Review（程式碼審查） 降低，CI（持續整合） 到底需要多少 Checker（檢查機制） 才足夠？Unit Test（單元測試）、Integration Test（整合測試）、SAST（靜態安全掃描）、Architecture Test（架構測試）、Mutation Test（變異測試） 是否越多越好？第 1、2、5 章
  • 問題本質：Checker 本身也有維護成本、Pipeline（管線） 時間與 False Positive（誤報）；核心不是數量，而是要控制哪些 Failure Mode（失敗模式）。第 1 章
  • 解法：從風險反推控制：Regression（回歸問題）→Test（測試）；Architecture Drift（架構漂移）→Architecture Test；Security（資安）→SAST；Breaking Change（破壞性變更）→Compatibility Check（相容性檢查）。採 Risk（風險） → Control（控制） → Checker。第 2 章
  • AI 時代差異：Agent（AI 代理） 可高速、跨大量檔案修改，因此原本靠工程師記得的規則，更需要變成機器強制。第 3、4 章
我的答案Checker 要幾道：最少要放幾道由風險決定，最多能放幾道由注意力決定，中間的增減靠資料調整。

第一句問要多少、是不是越多越好，第 1、2、5 章會回答。第二句的三種成本，我都付過，在第 1 章。第三句是從風險反推，在第 2 章。第四句說靠工程師記得的規則，要變成機器強制，在第 3、4 章。

我的答案先放在最下面：最少放幾道看風險，最多放幾道看注意力，中間靠資料調整。

從風險反推，就是先問這裡最可能壞在哪，再決定放什麼 Checker（檢查機制）、放在哪一站。題目舉了四種風險，我拿我們現在的狀況一個一個對。

Regression 是改了 A 壞了 B，靠 Unit 跟 Integration Test。我們 iOS 的測試只在本機跑，端到端靠我自己手動 smoke。Architecture Drift 是結構慢慢歪掉，要靠架構測試守依賴方向，我們只有 AI Board 那幾支 parity 測試勉強算。Security 要 SAST，再配 secret 跟套件掃描，這三種我們都沒有。Breaking Change 靠契約測試，只有 board-sync 跟 AI Board 之間的同步協定有。

所以最右邊這欄，老實說一個綠的都沒有。Fitness function（適應度函數） 那篇講的也是這個順序：先排出大家最在乎的屬性，再推出要放哪些檢查，之後定期回頭看。

我的例子：AI Board 補強同步的一個 PR

AI 那層同一個 commit（提交） 跑兩次 review（審查）：一次抓到真的並發 Critical（嚴重），5 分鐘後說 0 項

機器那層後來把它寫成測試，之後每次都會擋

誰抓得到這件事，Harness engineering 那篇把 coding agent（AI 代理） 常犯的錯分成三層。第一層機器就能可靠抓到，像重複程式碼、缺測試，便宜又確定。第二層 AI 只抓得到一部分，像暴力修法、過度設計，又貴又不穩。第三層兩邊都抓不穩，像誤解需求、做了不需要的功能，這種只能靠人。

第二層我自己踩過。AI Board 之前出過事，舊的狀態把新加的內容整份蓋掉，所以我開了一個 PR 補強同步。同一個 commit，我們自建的 Claude review 跑了兩次，第一次抓到一個真的 Critical：同時有兩筆修改進來，其中一筆會被悄悄蓋掉。5 分鐘後第二次跑，說 0 項。

AI 這次抓到算是碰巧，所以後來把它寫成測試，從 AI 那層搬到機器那層，之後每次都會擋。那這三層套回我們自己的流程，每一站到底有什麼？

10 月 27 號這版有 19 個檢核點。剛剛第三層那種機器和 AI 都抓不穩的錯，就要有人停下來看；放人還是放 agent，看風險。agent 檢查 3 次不過就交給人；人核准的是某一個版本，產物一改，核准就失效。

我在 ai-context（AI 工作脈絡資料夾） 放了幾份寫給 AI 看的規則，像 code review（程式碼審查） 的 SOP（標準作業程序） 就在裡面。其中一份是實作紀律檔，講 AI 實作時要守的事，標題就寫「強制規則」。畫面上這條是說：每個實作階段做完，必須跑 verification-before-completion（完成前先驗證） 跟 requesting-code-review（請人審查程式碼），不得跳過。一個是做完先驗證，一個是做完請 review。我的想法很簡單，AI 說做完之前，要先驗證過、也被 review 過。

寫得夠兇了吧？我把 135 天的對話紀錄翻過一遍，這兩個 skill 被觸發 0 次。原因是只有一份索引檔提到這份檔，沒有任何專案的 AGENTS.md 或 CLAUDE.md 會載入它，AI 根本沒讀到。上一章我們照風險決定要放哪些檢查，可是 AI 不跑，放了也等於沒放。

所以寫在 markdown 裡的「必須」，還是軟規則。就算 AI 讀到了，也不一定會照做。那它為什麼會略過？

R2 Harness engineering判定這一軸，就是它分的 computational（程式判定）和 inferential（AI 判斷）。

我覺得差在兩個問題。第一，要不要做：是 AI 想到才做，還是系統一定會觸發。第二，做得對不對：是 AI 自己判斷，還是程式判定。兩個一交叉，就是這四格。

剛剛那兩個 skill 都在左邊，要 AI 想到才會跑。requesting-code-review 在左下，最軟，對不對也是 AI 自己說了算。verification-before-completion 在左上，測試是程式判的，可是要 AI 想到才會跑，一樣 0 次。右下是半硬：我們自建的 Claude review 每個 PR 都自動跑，第 1 章那 232 次就是它，一定會跑，但判斷還是 AI。右上最硬：hook 擋下、CI 必過。這格我要誠實，我設的 hook 只有 1 支，還是記錄用的，沒有一支在擋品質。

Harness engineering 也是這樣分，它還提醒：只有事後檢查，agent（AI 代理） 會一直犯同樣的錯；只有事前引導，規則寫了也不知道有沒有用。所以我覺得不用每條都變硬，軟硬要搭配，但重要的那幾條要往右上搬。那要怎麼做硬？

答案 3 回答題目第四句的 AI 時代。題目說原本靠工程師記得的規則，要變成機器強制；我覺得換成 AI 也一樣，重要的規則不能靠 AI 記得。觸發交給系統，判定能寫成程式就寫，交接時附上驗證結果。像 board-sync 的 benchmark，AI 說做完了，卻沒有做，所以不能只聽它說。

答案 4：最多能放幾道，看人的注意力。我開的 86 個 PR 上，人親手寫的對話只有百分之三左右，人讀得完的就這麼多。中間要加還是要減，就靠剛剛那個循環：每一道響了幾次、抓到幾次真問題都記下來，該收斂的收斂，該淡出的淡出。

讀物這邊，R1 的作者之一 Uncle Bob，媒體轉述他說現在只核准規格、不讀 code。我自己也不讀 code，我看的是驗證結果和 AC，這就是答案 3 在講的事。

合起來，就是我一開始放在題目下面的答案：下限看風險，上限看人的注意力，中間靠資料調整。最後，我留三句話和三個問題給大家。
